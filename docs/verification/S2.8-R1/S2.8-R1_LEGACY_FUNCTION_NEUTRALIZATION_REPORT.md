## A. Executive summary

### A.1 Resultado

A auditoria confirmou que `investfacil.apply_table_security()` era chamada apenas por V2 e V3, durante a criação do schema e da tabela `simulations`. Não há chamada em Java, triggers, policies, default privileges ou migrations posteriores.

A função foi **removida** na V7 local com `DROP FUNCTION IF EXISTS ...` (sem `CASCADE`). A remoção:

- elimina a possibilidade de recriar `app_rw`;
- elimina a possibilidade de alterar RLS/policies/grants por essa função;
- mantém V2/V3 funcionais em banco vazio, porque as chamadas ocorrem antes da V7;
- mantém o upgrade V6 → V7 funcional;
- deixa nove funções permanentes com `search_path = ''` e EXECUTE mínimo;
- mantém 68 policies `s24_*`, 18 tabelas com RLS + FORCE e zero `app_rw`.

## C. Auditoria da função legada

### C.1 Definição

A função original, criada na V2, percorria `pg_tables`, habilitava RLS e recriava a policy:

```sql
CREATE POLICY app_rw ON investfacil.<tabela>
  FOR ALL TO investfacil_app
  USING (true) WITH CHECK (true);
```

Ela era `SECURITY INVOKER`, owner `investfacil_migrate`, sem `proconfig` inicialmente.

### C.2 Dependências encontradas

| Dependência | Evidência | Conclusão |
|---|---|---|
| V2 | `SELECT investfacil.apply_table_security();` | chamada de criação inicial; ocorre antes da V7 |
| V3 | `SELECT investfacil.apply_table_security();` | chamada ao adicionar `simulations`; ocorre antes da V7 |
| V4/V5/V6 | nenhuma chamada | não dependem da função |
| Java | nenhuma referência | não há chamada de runtime |
| Triggers | nenhuma trigger usa a função | remoção não quebra trigger |
| Policies | nenhuma policy usa a função | remoção não quebra RLS |
| Default privileges | nenhum default privilege da função | remoção não quebra grants |
| Scripts operacionais | apenas documentação histórica menciona | não há execução operacional |
| Testes | teste antigo verificava EXECUTE do runtime | atualizado para ausência/negativa |

A V6 **não depende** da função após a instalação. A V7 é aplicada depois de V6 e pode removê-la com segurança.

### C.3 Decisão: Opção A — remover

A remoção é preferível a manter uma função que apenas lança exceção:

- elimina totalmente a superfície de ataque;
- não deixa assinatura residual que possa ser recriada/sobrescrita;
- não exige conceder EXECUTE a ninguém;
- não deixa caminho para `app_rw`;
- o `DROP` sem `CASCADE` falha se houver dependência inesperada, em vez de remover objetos silenciosamente.

## D. SQL final da V7

### D.1 Ordem

1. `search_path = ''` nas **nove** funções permanentes;
2. `REVOKE ALL ... FROM PUBLIC` nas nove;
3. `GRANT EXECUTE` para `investfacil_app` e `investfacil_migrate`;
4. `ALTER DEFAULT PRIVILEGES ... REVOKE EXECUTE ON FUNCTIONS FROM PUBLIC`;
5. `DROP FUNCTION IF EXISTS investfacil.apply_table_security();`

### D.2 Remoção

`apply_table_security()` não aparece mais no catálogo após a V7.

## G. DatabaseSecurityGuard

### G.1 Estado final

O guard agora:

- valida o baseline V6 com a função legada presente;
- detecta V7 por **nove** funções com `search_path` fixo **e ausência** de `apply_table_security()`;
- falha se a função legada reaparecer depois do hardening;
- falha se a V7 for exigida e não estiver instalada;
- falha se o schema for mais novo que V7;
- mantém as verificações de RLS/FORCE, 68 policies, zero `app_rw`, owners, trigger, role runtime e ACLs;
- não consulta `has_function_privilege` em função ausente.
