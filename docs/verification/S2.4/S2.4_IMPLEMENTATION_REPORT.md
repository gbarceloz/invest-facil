## A. Resumo

### A.1 Objetivo

Implementar a arquitetura aprovada na S2.3:

1. contexto de identidade por transação, derivado do JWT/principal e nunca de parâmetro do cliente;
2. `set_config(..., true)` na conexão da transação, sem `SET` de sessão;
3. migration V6 com policies específicas por tabela, `USING`/`WITH CHECK`, `FORCE RLS` e privilégios mínimos;
4. fluxos de autenticação, seed e admin com contexto explícito;
5. testes A×B, concorrência, rollback, Hikari e privilégios contra PostgreSQL real.

### A.2 Resultado

- V6 criada e aplicada com sucesso em PostgreSQL 17.12 real (Testcontainers).
- A aplicação foi executada com `investfacil_runtime` (LOGIN INHERIT, membro de `investfacil_app`), não com superuser.
- O Flyway foi executado com `investfacil_migrate` **não-superuser**, dono do schema/tabelas, comprovando que a V6 funciona sem `postgres`.
- O contexto é aplicado no `doBegin` do `UserContextTransactionManager`, depois da abertura da transação JPA e antes da primeira query.
- A suíte completa passou: **57 testes, 0 falhas, 0 erros, 0 ignorados**.
- O novo teste de RLS tem **10 testes** e usa o role runtime real; não mocka repositories para o isolamento.
- Frontend permaneceu byte a byte no baseline conhecido.
- V1–V5 permanecem intactas; apenas V6 foi adicionada.

### A.3 Por que PASS WITH LIMITATIONS

O núcleo foi implementado e comprovado localmente. As limitações estão registradas na seção G e em A.4:

- `mvn clean test` não pôde concluir o `clean` porque processos Java **preexistentes do usuário** mantêm o jar `backend/target/investfacil-api-0.1.0-SNAPSHOT.jar` aberto. `mvn test` sem `clean` passou 57/57. Nenhum processo foi encerrado.
- Não houve validação remota (Supabase/Lab), por proibição explícita.
- `DemoDataInitializer` está desabilitado por padrão; o código recebeu contexto explícito, mas esse caminho não foi executado em teste de runtime.
- Não houve E2E de navegador; a validação é HTTP MockMvc + PostgreSQL real.
- RLS não protege contra SQL arbitrário executado pelo próprio runtime: qualquer SQL capaz de chamar `set_config` pode forjar o contexto. O desenho assume aplicação parametrizada e não comprometida. Isso é defesa em profundidade, não uma fronteira contra SQL injection.

### C.2 Contexto

`UserContext` mantém, por thread:

```text
app.current_user_id          UUID do JWT/principal ou usuário descoberto no fluxo
app.current_role             USER/ADMIN lido do banco
app.auth_email               e-mail normalizado de login/cadastro/recuperação
app.auth_refresh_hash        SHA-256 do refresh token apresentado
app.auth_email_token_hash    SHA-256 do token de verificação/reset
app.flow                     LOGIN | REGISTER | REFRESH | LOGOUT | EMAIL_VERIFY |
                             PASSWORD_RESET | MFA | RESEND_VERIFICATION | REQUEST | ADMIN | SEED
app.seed                     true somente no seed interno
```

Regras:

- `userId` nunca vem de DTO, path, query, header ou body comum. Vem do `sub` do JWT validado, do principal autenticado, do token opaco já validado pelo backend ou do usuário criado no próprio fluxo.
- `role` nunca vem do claim; é lida de `users.role` pelo `JwtAuthenticationFilter`.
- O cliente não define `seed`, `flow` ou hash; esses valores são calculados no backend.
- `set_config` usa `PreparedStatement` com parâmetros; não há concatenação de valores de contexto.
- Valores vazios são gravados como string vazia; as policies usam `NULLIF(current_setting(..., true), '')`.

### C.3 Integração Spring/transação

`UserContextTransactionManager extends JpaTransactionManager`:

```text
doBegin(transaction, definition)
  -> super.doBegin(...)          // abre transação JPA e vincula EntityManager
  -> context.applyToCurrentTransaction()
       -> EntityManagerHolder da transação
       -> Session.doWork(connection)
       -> SELECT set_config(..., true)
```

- `REQUIRES_NEW` recebe nova aplicação de contexto.
- Transação aninhada reutiliza o contexto externo.
- Quando o contexto muda dentro da transação (registro, refresh, verificação, reset), `UserContext.applyToCurrentTransaction()` reaplica na mesma conexão.
- `open-in-view=false`; não há transação de request inteiro.
- `set_config(..., true)` é local à transação: commit/rollback remove o valor. O Hikari devolve a conexão sem identidade.
- O `JwtAuthenticationFilter` limpa o `ThreadLocal` em `finally`, inclusive em 401/erro.

### C.4 Ordem de identidade

```text
JWT assinado
  -> JwtAuthenticationFilter: sub -> UserContext.userId
  -> users SELECT self (policy)
  -> User carregado do banco: role
  -> UserContext.userId + role + flow REQUEST/ADMIN
  -> Controller
  -> Service(@Transactional)
  -> UserContextTransactionManager.doBegin: set_config local
  -> Repository/SQL com RLS
  -> commit/rollback: contexto local expira
  -> filter finally: UserContext.clear()
```

Fluxos pré-autenticação usam apenas o contexto mínimo:

| Fluxo | Antes da primeira query | Depois de localizar o usuário |
|---|---|---|
| Registro | `auth_email` + `flow=REGISTER` | `userId` e role USER; reaplica na transação |
| Login | `auth_email` + `flow=LOGIN` | `userId` e role; auditoria/tokens |
| Refresh | `auth_refresh_hash` + `flow=REFRESH` | `userId` e role; reaplica para rotação |
| Logout | hash do refresh (se houver) + `flow=LOGOUT` | `userId` do token; revogação/auditoria |
| Verificação de e-mail | hash do token + `flow=EMAIL_VERIFY` | `userId`; reaplica |
| Reset | hash do token + `flow=PASSWORD_RESET` | `userId`; reaplica |
| MFA verify | `flow=MFA`; o serviço valida o challenge | `userId` e role |
| Seed | `seed=true` + `flow=SEED` | sem usuário |
| Admin | `userId` + role ADMIN + `flow=ADMIN` | sem contexto adicional |

### C.5 Detalhes de JPA que precisaram de ajuste

- `User` recebeu `@DynamicUpdate` para que updates de perfil/login/MFA não incluam todas as colunas por padrão. Isso reduz o risco de alteração acidental de `role`/`email` e é compatível com privilégios de coluna futuros.
- `QuizQuestion` recebeu `@Immutable`. Sem isso, o dirty-check do Hibernate tentava atualizar a entidade carregada no submit do quiz; sob RLS sem policy de UPDATE, a atualização afetava 0 linhas e gerava `StaleObjectStateException`. A entidade é somente leitura para o runtime; o seed apenas insere novas questões.
- `AuthService.login` continua sem transação externa. Cada Repository abre sua transação e recebe o contexto vigente; a auditoria de falha continua em transação própria.
- `AuthAuditService` não foi alterado; a limitação de auditoria em rollback de `register` permanece documentada.

## G. Threat model

### G.1 Riscos resolvidos ou reduzidos

| Risco | Tratamento |
|---|---|
| Query sem filtro de `user_id` | RLS por owner em todas as tabelas privadas. |
| IDOR em progresso, quiz, XP, conquistas, simulações, tokens | `USING`/`WITH CHECK` por usuário; testes A×B. |
| Inserir registro com `user_id` de outro | `WITH CHECK` + política owner; teste. |
| Alterar `user_id`/ownership | `WITH CHECK` e trigger de `users`; testes. |
| Escalar `role` para ADMIN | Trigger não confia no GUC; teste com ADMIN forjado. |
| Alterar `id`/`email` de usuário | Trigger; teste. |
| Ler auditoria de todos | `REVOKE SELECT` em `auth_event`; teste. |
| Ler tokens/hashes de todos | Policies owner/hash; tokens de B invisíveis a A. |
| Admin escrever como usuário comum | `is_admin()` exige role do banco + flow ADMIN; teste. |
| Seed escrever como usuário comum | `seed=true` explícito; teste. |
| `SET` de sessão vazar no Hikari | `set_config(..., true)`; teste de commit/rollback. |
| ThreadLocal vazar entre requests | `finally` no filtro; teste. |
| Runtime assumir migrate/DDL | Sem membership/ownership/DDL; teste. |
| `postgres` como runtime | Teste usa runtime; V6 não depende de `postgres`. |

### G.2 Riscos residuais

1. **SQL arbitrário pelo runtime:** `investfacil_runtime` pode executar `SELECT set_config('app.current_user_id', ...)` se conseguir executar SQL. RLS não é uma fronteira contra SQL injection/app comprometido. A proteção efetiva é SQL parametrizado, autorização de endpoint e revisão de código.
2. **Contexto forjado:** `app.current_role`, `app.flow` e `app.seed` são GUCs de sessão/transação. Um SQL arbitrário pode forjá-los. O trigger de `users` bloqueia role/id/email mesmo com `role=ADMIN` forjado; as policies de conteúdo/admin/seed não têm essa proteção adicional.
3. **`postgres`/superuser:** continua com `BYPASSRLS`; não deve ser o datasource de runtime. Não foi adicionada guarda de startup; a configuração de produção deve garantir `SPRING_DATASOURCE_USERNAME=investfacil_runtime`. O teste de privilégios cobre o role runtime, não impede uma configuração errada.
4. **`investfacil_migrate`:** tem policy `FOR ALL` e é confiável por definição. Suas credenciais e membership precisam ser protegidas; o runtime não é membro.
5. **Auditoria/XP:** `auth_event`, `xp_ledger` e `user_achievements` são append-only para UPDATE/DELETE, mas o runtime pode inserir eventos/XP/conquistas do próprio usuário. RLS valida ownership, não regra de negócio. Mitigação futura: função `SECURITY DEFINER` ou role de escrita separada.
6. **Auditoria em rollback:** eventos gravados dentro de uma transação de negócio podem ser revertidos; `register` duplicado é exemplo. `REQUIRES_NEW`/outbox é melhoria futura.
7. **`auth_email`:** a policy de leitura por e-mail é necessária para login/cadastro/recuperação. O endpoint usa respostas genéricas, mas a linha é visível ao backend durante o fluxo. Não há leitura cross-user por endpoint.
8. **`lesson_articles`:** órfã, sem acesso do runtime. Se for usada, exige V7 e policy própria.
9. **`VideoService.upload`:** a transação inclui chamada ao Storage; o contexto não deve justificar transações longas.
