## A. Executive summary

### A.1 Objetivo

Revisar independentemente a implementação S2.4 e decidir se a V6 está pronta para a próxima etapa de validação no Supabase Lab.

### A.2 Resultado

- A implementação S2.4 foi auditada diretamente no código, SQL, grants e testes, sem aceitar automaticamente o relatório anterior.
- Nenhum bypass crítico de RLS foi encontrado nos cenários locais.
- A×B, INSERT/UPDATE/DELETE cross-user, ownership, tokens, auditoria, seed, admin, MFA, reset/logout, rollback, `REQUIRES_NEW`, concorrência e Hikari foram exercitados com PostgreSQL 17.12 real.
- A V6 foi aplicada pelo Flyway como `investfacil_migrate` **não-superuser**, com a aplicação rodando como `investfacil_runtime`.
- **58 testes Maven passaram**, 0 falhas, 0 erros, 0 ignorados, exit code 0.
- **10 testes específicos de RLS** passaram com o runtime real.
- **5 testes E2E de navegador** passaram, mas o harness E2E usa `postgres` superuser; isso valida a UI e a autenticação, **não** o isolamento RLS.
- Foram implementados e testados:
  - `DatabaseSecurityGuard` de startup, somente leitura, com padrão strict;
  - validação do `DemoDataInitializer` sob seed/RLS e idempotência;
  - bloqueio do `DemoDataInitializer` no profile `prod`.
- Frontend permaneceu intacto.
- V1–V5 permanecem intactas.

### A.3 Por que PASS WITH LIMITATIONS

Não há falha crítica conhecida de isolamento. As limitações são de validação/ambiente:

1. `mvn clean test` continua bloqueado por processos Java preexistentes do usuário que mantêm o jar aberto. Nenhum processo foi encerrado. `mvn test` passou 58/58.
2. Não houve validação remota no Supabase Lab, por proibição explícita.
3. O E2E de navegador passou, mas usa `postgres` superuser; não é evidência de RLS A×B. A evidência de RLS é o teste backend com `investfacil_runtime`.
4. RLS não é uma barreira absoluta contra SQL injection/GUC forgery; é defesa em profundidade.
5. O guard de startup verifica o estado esperado da V6 por catálogo (funções, policies, FORCE, grants), mas não lê `flyway_schema_history` como runtime, pois isso exigiria ampliar privilégios.
6. O guard acopla-se intencionalmente ao conjunto de 18 tabelas e ao conjunto de policies da V6; migrations futuras precisam atualizar o guard.
7. Não há jobs `@Async`/`@Scheduled` no código atual; se forem adicionados, precisarão propagar/limpar o contexto explicitamente.

### A.4 Decisão de release

**V6: READY FOR LAB.**

Não é uma aprovação para produção. A próxima etapa deve aplicar V6 no Lab descartável autorizado, executar a mesma matriz com runtime real, validar Advisors/TLS e decidir produção somente depois.

## D. Context manager

### D.1 Revisão técnica

`UserContextTransactionManager extends JpaTransactionManager`:

- `doBegin` chama `super.doBegin` e então `UserContext.applyToCurrentTransaction()`.
- `applyToCurrentTransaction` obtém o `EntityManagerHolder` da transação, usa `Session.doWork` e executa um único `SELECT set_config(..., true)` para os sete valores.
- `set_config(..., true)` é local à transação; commit/rollback removem o valor.
- `AuthService` chama `bindUser`/`applyToCurrentTransaction` quando descobre o usuário no meio de registro, refresh, verificação, reset ou logout.
- O filtro JWT limpa o `ThreadLocal` no início e no `finally`.
- `ContentSeeder` e `DemoDataInitializer` usam contexto seed e limpam no `finally`.

### D.2 Cobertura de transações

| Cenário | Evidência |
|---|---|
| Transação normal/read-only | `UserService.findById`, catálogo, auth; testes 58/58 |
| Troca de contexto dentro da transação | `transactionContextSwitchNestedTransactionAndRollbackAreSafe` |
| `REQUIRES_NEW` | mesmo teste, com conexão nova |
| Rollback | transação de teste + query de `current_setting`; contexto residual vazio |
| Commit | `set_config` local testado diretamente |
| Concorrência | duas threads com A/B e `userService.findById` |
| Hikari | conexão reutilizada sem `app.current_user_id` após commit/rollback |
| Thread reutilizada | cleanup do filtro e `ThreadLocal` |
| Exceções de auth | login inválido, token inválido, MFA inválido, 401 |
| Contexto ausente | `users` retorna 0; endpoint privado 401 |
| Contexto inválido | UUID inválido falha fechado (`SQLException`) |

### D.3 Riscos e limitações do contexto

1. **Somente JPA:** o contexto é aplicado pelo `JpaTransactionManager`. Não há uso de JDBC direto para dados de usuário no código de produção; o único JDBC é o guard, que só lê catálogo. Se um `JdbcTemplate` for introduzido no futuro fora do transaction manager, precisará de tratamento explícito.
2. **Async/scheduled:** não existem `@Async`, `@Scheduled`, `Executor` ou threads de background de usuário. O `ThreadLocal` não se propaga automaticamente; jobs futuros precisarão de contexto explícito e cleanup.
3. **Nested savepoint:** não há uso de `PROPAGATION_NESTED`; o teste cobre `REQUIRES_NEW`. A semântica de savepoint deve ser revista se for adotada.
4. **DoCommit/doRollback:** não foram sobrescritos; a segurança vem do `set_config` local e do cleanup no filtro/seeders. O teste confirma que não há valor residual na conexão.
5. **Filtro duplicado:** o `JwtAuthenticationFilter` é um bean `Filter`; a revisão não alterou essa configuração. O cleanup duplo é idempotente, mas a duplicação de execução deve ser observada em futura otimização.
6. **Contexto presumido:** se um SQL arbitrário executar `set_config`, pode forjar GUCs. O trigger de `users` bloqueia role/id/email mesmo com ADMIN forjado; as policies de conteúdo/seed/admin não têm uma segunda barreira criptográfica. RLS não é barreira absoluta.

### E.1 Implementação

Arquivo: `backend/src/main/java/com/investfacil/api/common/security/DatabaseSecurityGuard.java`

SHA-256: `2dd91b2bbb24bb213a21d4b327a663beb8af5c1a28eb4bb8273cbb1c9f58d64e`

Características:

- `ApplicationRunner` com `@Order(0)`, antes de `ContentSeeder` (1) e `DemoDataInitializer` (2).
- Somente SELECTs de catálogo/consultas de privilégio.
- Não altera schema, policies, grants, dados ou roles.
- Não registra connection string, senha, token ou credencial; loga apenas o nome do role.

- Testes usam `src/test/resources/application.properties` com `app.security.guard.strict=false`; `application-dev.yml` tem a mesma exceção explícita para o banco local/superuser. Produção não contém esse recurso de teste.

### E.2 Checks implementados

- role atual/memberships com `SUPERUSER`, `BYPASSRLS`, `CREATEDB`, `CREATEROLE`;
- `ADMIN OPTION` em membership;
- membership em `investfacil_migrate` (`MEMBER` ou `SET`);
- membership obrigatória em `investfacil_app`;
- runtime owner de tabela protegida;
- schema `investfacil`, 18 tabelas de aplicação, owner `investfacil_migrate`;
- `relrowsecurity` e `relforcerowsecurity` nas 18 tabelas;
- ausência de `app_rw`;
- policies V6 por tabela e contagem esperada por tabela;
- policies de migração nas 18 tabelas;
- ausência de `USING/WITH CHECK true` em tabela privada, exceto `s24_migration_all`;
- matriz de grants (SELECT/INSERT/UPDATE/DELETE) por tabela;
- ausência de `CREATE` no schema;
- ausência de `EXECUTE` em `apply_table_security`;
- presença das funções V6, do trigger `s24_users_guard` e das policies obrigatórias;
- versão/compatibilidade V6 inferida pelo catálogo, pois o runtime não tem SELECT em `flyway_schema_history` (least privilege).

### E.3 Execução

- O guard passou no startup do teste com `investfacil_runtime`.
- O guard falhou, como esperado, quando instanciado com um DataSource superuser e `Environment` com profile `prod`; a mensagem contém “superuser”.
- Nos testes legados com superuser, o guard emite warning e não falha, porque a exceção de teste está explícita; o profile `prod` não usa essa exceção.
- O guard não foi testado individualmente contra todas as combinações de policy ausente/RLS desabilitada; essas verificações existem no código e a matriz de catálogo é exercitada no runtime seguro. A validação destrutiva de cada falha fica para o Lab/CI.

### E.4 Limitações do guard

- Acoplado ao conjunto exato de 18 tabelas e às contagens de policies da V6; migrations futuras devem atualizar o guard junto com a migration.
- Não lê `flyway_schema_history`; verifica os artefatos da V6.
- Roda como `ApplicationRunner`, após o servidor web já ter sido inicializado pelo Spring Boot. O processo falha antes de aceitar tráfego funcional na prática, mas existe uma janela de startup; o orquestrador deve tratar exit code.
- `application-dev.yml` permite strict=false para superuser local; isso é uma exceção de desenvolvimento e não deve ser usado em produção. O profile `prod` força strict=true.

## I. Threat model

### I.1 O que RLS/contexto protege

- Query esquecida sem filtro de ownership.
- Acesso acidental cross-user em SELECT/INSERT/UPDATE/DELETE.
- Leitura de progresso, quiz, XP, conquistas, tokens, e-mail e simulações de outro usuário.
- Inserir/transferir ownership para outro usuário.
- Alteração de `id`, `role` ou `email` via app bug, com trigger.
- Leitura de auditoria e de `lesson_articles` pelo runtime.
- Escrita de conteúdo comum sem contexto seed.
- Uso de vídeo não publicado por usuário comum.
- Vazamento de `set_config` de sessão entre requisições Hikari.
- Runtime assumir DDL/migrate/owner/BYPASSRLS.

### I.2 O que RLS/contexto NÃO protege

- SQL injection capaz de executar SQL arbitrário e chamar `set_config` com outro UUID/role/seed.
- Credenciais runtime comprometidas.
- Superuser/BYPASSRLS no datasource.
- Vulnerabilidade de autorização no backend (endpoint que chame o service errado).
- Abuso de regra de negócio: XP, conquistas, score de quiz, progresso de aula, simulação.
- Auditoria forjada pelo próprio usuário (`auth_event` INSERT) ou perda de auditoria em rollback.
- `users` self-update de `verified`, MFA, password por SQL direto; não há endpoint sem senha/token, mas a policy não valida a regra.
- `auth_email` lookup amplo, necessário para login/reset.
- `quiz_questions.correct_index` é acessível a quem executa SQL como runtime; não há column-level privilege.
- Processos/credenciais administrativas fora do banco.

### I.3 Mitigações recomendadas

- manter SQL 100% parametrizado e proibir SQL dinâmico;
- manter runtime sem DDL/owner/BYPASSRLS/migrate;
- guard de startup em produção;
- monitorar/logar falhas de guard, 401, 403, erros de RLS e acessos administrativos;
- separar ainda mais conteúdo/seed/admin em role/datasource próprio se o risco justificar;
- avaliar funções `SECURITY DEFINER`/outbox para ledgers e auditoria;
- decidir `lesson_articles`;
- testar Advisors/TLS no Lab.

## M. Release decision

### V6: **READY FOR LAB**

**Justificativa técnica:**

- A V6 foi aplicada com sucesso por `investfacil_migrate` não-superuser, sem `postgres`.
- O runtime real `investfacil_runtime` passou A×B, ownership, tokens, auditoria, seed, admin, MFA, reset/logout, rollback, Hikari, concorrência e privilégios.
- Nenhum bypass crítico de RLS foi encontrado.
- O startup guard foi implementado, passa no runtime seguro e falha com role privilegiado em modo estrito.
- O `DemoDataInitializer` foi executado sob seed/RLS e é idempotente; produção é bloqueada.
- Frontend está intacto; V1–V5 intactas.
- A UI E2E passou 5/5, embora com a limitação de superuser do harness.

**O que ainda falta antes de produção:**

1. aplicar V6 no Lab descartável autorizado, como `investfacil_migrate`, e rodar com `investfacil_runtime`;
2. repetir A×B, auth, seed, admin, concorrência, rollback e guard no Lab;
3. validar Advisors, TLS fim-a-fim e configuração do Render/Supabase;
4. criar um E2E de runtime (não superuser) ou um teste backend equivalente no pipeline;
5. executar `mvn clean test` em ambiente limpo/CI sem jar preexistente;
6. revisar `lesson_articles`, `auth_event`/XP business rules e eventual separação de role de conteúdo/seed;
7. aprovar a V6 para produção somente após esses gates.

Não iniciar a etapa remota sem autorização explícita.
